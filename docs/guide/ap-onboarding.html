SDA Pathfinder Field Guide

How to run the AP Onboarding workflow, read the topology it draws, and find the command output behind every finding.

What this tool does

SDA Pathfinder answers one question per workflow by reading live state off the fabric and grading it. The AP Onboarding workflow answers: why is this access point not joining, or not serving the SSIDs it should?

It logs into the devices through RADKit, runs around forty read-only show commands across the fabric edge, the WLC and the control planes, and turns the output into individually graded checks. Nothing is ever configured. The result is a topology you click through, where each node carries the verdict for the checks that ran against it.

The value over doing this by hand is sequencing. The checks run in dependency order and stop a chain when its precondition fails, so you get the first thing that actually broke instead of fifty downstream symptoms.

Before you start

  • A RADKit service that can reach the fabric, and its service serial.
  • Your Cisco SSO credentials.
  • The three inputs the workflow needs: the fabric edge the AP is cabled to, the AP's Ethernet MAC, and, if the deployment uses an RSA Standalone Server, the Catalyst Center name.
The MAC is the Ethernet MAC, not the radio MAC. This is the single most common input error. The radio MAC is what you see in the LISP database; the Ethernet MAC is what Catalyst Center and show ap summary index by, and it is what the tool expects. They differ, usually in the last octet.

Running a case

1 · Pick the workflow

The landing page splits workflows by whether they need device access. The four RADKit-based ones read live state and need an SSO login. The off-line section is for replaying captured output and is not available yet.

2 · Log in

Enter your Cisco address, leave the domain on PROD unless you have been told otherwise, and use the SSO login method. The page tells you which workflow you are authenticating for.

3 · Connect to the service

Enter the serial of the RADKit service that fronts the fabric you are troubleshooting. If you support several customers, this is the field that selects between them.

4 · Give it the AP

FieldWhat it is
XTR Inventory Management IPThe management IP of the fabric edge the AP is physically cabled to. It must be an Edge node — a Border will not do, because the access tunnel and L2 LISP registration the tool checks live on the edge.
Catalyst Center nameOnly needed when an RSA Standalone Server is in use. Leave it blank otherwise.
Access Point MACThe AP's Ethernet MAC, in any common format.

Press Run. Checks begin streaming immediately; you do not wait for the whole run to finish before reading results.

Reading the topology

The canvas builds as the run proceeds. Devices appear once they are discovered, and links appear once the tool has evidence for them. An empty area is not a missing device — it is a device the tool has not reached yet.

Node badges

Every device carries one coloured dot in its top-right corner. It reflects the worst result among the checks that ran against that device, so a single amber check turns the node amber.

BadgeStatusMeaning
PendingQueued, not started.
RunningExecuting now.
OKVerification passed.
WarnA real concern, but the tool could continue. Most fabric faults land here.
FailThe check could not complete, and downstream checks may be unsafe. Later checks in that chain are skipped.
SkipNot applicable to this run, or skipped because something upstream failed.
Warn is the interesting status, not Fail. A fabric problem is graded Warn: the tool read the device fine, and what it read was wrong. Fail means the tool itself could not proceed — an unreadable command, an unreachable device. When triaging, read the Warns first.

Node labels and roles

Each node is labelled with its hostname and its fabric roles in brackets. A device holding several roles shows all of them, and a combined Border plus Control Plane carries a B+C glyph on its icon. Roles are promoted during the run as evidence arrives: the WLC starts as [WLC] and becomes [WLC, Fabric WLC] once the tool confirms it is fabric-enabled.

Clicking a node

Click any device to open its findings panel. The tally in the panel header is scoped to that node, not to the whole run, so the numbers change as you click around. The panel lists every check that ran against the device; click a row to expand its full output.

Findings are written to be read on their own. They name the device, the interface and the measured value, so you can paste one into a case note without rewriting it. A graded finding states what was read first, then what it means — the WLC Platform example above lists the platform, uptime and redundancy state, then explains that HA is configured but not operating as a pair, that onboarding is unaffected, and what would break on a failover.

The fabric SSID mark

When the AP is on air with fabric SSIDs, a green WiFi mark appears beside it, labelled with the SSID names. This is the fastest answer to "is this AP actually serving the fabric WLANs" — if the mark is absent, it is not, whatever the WLC configuration says.

Edges between nodes

Links are labelled with what they represent. Solid lines are physical; dotted lines are protocol relationships the tool verified.

  • Interface name (Te1/0/14) — the physical cable from the AP to its edge.
  • Ac0 · VXLAN — the access tunnel carrying the AP's client traffic.
  • CAPWAP Control — the AP's control session to the WLC, drawn across the fabric path it actually takes.
  • LISP Session — an edge or WLC registered with a control plane.
  • IP Underlay — underlay reachability between fabric nodes.

Getting the evidence out

ButtonWhat you get
Download Logcollection_logfile.txt — the raw command output, every command the run issued and everything the devices returned. This is what you attach to a case or read when you disagree with a verdict.
Download ChecksA PDF of the graded checks and their findings. Suitable for a case note or a customer summary.

Download the log before you close the tab. Logs are tied to your session. If the server restarts, or you come back to an old tab, the log is gone and you will have to re-run the case.

The build version and commit are shown in the top-right of the topology header. Quote them when reporting a problem with the tool itself.

A triage order that works

  1. Check the AP appeared at all. No AP node means the Ethernet MAC did not match anything on the WLC — re-check the MAC before anything else.
  2. Read the Warns, not the Fails. Fails are usually the tool being blocked; Warns are the fabric being wrong.
  3. Work outward from the AP. AP, then edge, then control planes, then WLC. A broken access tunnel makes the WLC's view meaningless.
  4. Check for the green SSID mark. Present means the AP is genuinely on air with the fabric WLANs; absent means it is not, regardless of what the policy tag claims.
  5. Open the log for anything you doubt. Every verdict traces back to command output you can read yourself.
